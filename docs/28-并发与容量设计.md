# 并发与容量设计

## 1. 结论

当前架构是**模块化单体 + 单进程内存状态**，适合单机中小型社区，不属于已经完成横向扩展设计的高并发架构。

- **SQLite**：适合低写入、单节点场景，不建议作为高并发生产库。
- **MySQL / PostgreSQL**：当前连接池默认 50 个连接、20 个空闲连接，可支撑单实例数百到上千简单请求/秒，具体取决于查询和硬件，需以压测为准。
- **多实例部署**：当前 SSE Hub、限流器和部分缓存是进程内状态，直接多实例会出现通知丢失、限流不共享、连接分布不均。需要 Redis 等共享设施。

因此回答是：**有基础并发保护，但没有完成大规模高并发设计**。

## 2. 已有的并发措施

- HTTP Server：
  - `ReadHeaderTimeout 10s`
  - `ReadTimeout 30s`
  - `IdleTimeout 120s`
  - `MaxHeaderBytes 1 MiB`
  - SSE 不设置全局 `WriteTimeout`，避免长连接被误杀
- 数据库连接池：
  - 默认 `MaxOpen=50`、`MaxIdle=20`、`ConnMaxLifetime=30m`
  - SQLite 自动限制为 4 个连接，降低写锁竞争
- 通知 SSE 改为事件驱动：
  - 进程内 Hub 按用户分发，不再每 3 秒轮询数据库
  - 每个连接一个 goroutine + 有缓冲 channel，慢客户端丢弃中间更新
  - 25 秒心跳
- 限流：
  - 固定窗口内存桶，按 IP + 路由分桶
  - 定期清理过期桶
- 请求体上限、CSP、CSRF、权限中间件。
- 后台任务与通知事件使用进程内 Event Bus；当前为同步分发。
- 搜索使用数据库 FTS/LIKE；Sitemap/RSS 有 HTTP 缓存头。
- 分类列表增加 30 秒进程内缓存，分类增删改与主题/回复写入时主动失效。
- 私信列表改为批量读取会话、对方、最后消息与未读数，移除逐会话 N+1 查询。
- 限时禁言/封禁在用户身份读取时自动过期，避免依赖定时任务。

## 3. 当前瓶颈

1. **SQLite 单写者模型**：写并发高时会产生锁等待，不适合多实例共享。
2. **每请求会话查询**：Session 从数据库读取；高 QPS 下会话表是热点。
3. **列表 COUNT 查询**：首页、后台、用户主页等每个请求都执行 COUNT。
4. **私信列表 N+1 已修复**：现在批量读取对方、最后消息与未读数；仍需关注大分页和搜索条件。
5. **内存状态不可横向共享**：
   - 通知 Hub 只在当前进程内广播；
   - 限流桶只在当前进程内计数；
   - 站点布局缓存、设置缓存为进程内。
6. **同步事件总线**：通知、搜索索引等处理在请求链路内同步执行，写请求延迟受下游影响。
7. **缓存使用不足**：`cache` 抽象存在，但分类、标签、热门列表等热点读仍未接缓存。
8. **无读写分离**：所有查询走主库。
9. **SSE 连接数**：每连接一个 goroutine 和 channel，单机可支撑数千连接，但受文件描述符和内存限制。

## 4. 单机容量参考

以下是工程估算，不是压测结论：

| 数据库 | 读请求 | 写请求 | 适用 |
| --- | --- | --- | --- |
| SQLite | 约 100–300 RPS | 低并发写入 | 小型社区、预览、单机 |
| MySQL / PostgreSQL | 数百–1000+ RPS | 取决于事务与索引 | 中型社区 |
| 多实例 + Redis + PostgreSQL | 可按实例水平扩展 | 需共享限流/通知/缓存 | 大型社区 |

实际容量必须以目标硬件、页面查询数、缓存命中率和压测结果为准。

## 5. 高并发改造路线

### P0
1. 生产使用 PostgreSQL 或 MySQL，禁止多实例共享 SQLite。
2. 压测首页、主题页、登录、发帖、通知 SSE。
3. 修复私信列表 N+1：批量查询最后消息、未读数、对方用户。
4. 为分类、标签、站点布局、热门列表增加短 TTL 缓存。
5. 将搜索索引、邮件、通知等非关键路径移入异步队列。

### P1
1. Redis：
   - 共享 Session
   - 共享限流桶
   - SSE Pub/Sub（多实例通知）
   - 页面/列表缓存
2. 数据库读副本；读请求按场景路由。
3. 对象存储 + CDN 承载上传与静态资源。
4. 连接池与超时按数据库和实例数重新计算。
5. 增加慢查询日志、连接池指标、SSE 连接数指标。

### P2
1. 按模块拆分读服务或独立搜索服务。
2. 热点帖子缓存与分页游标。
3. 多地域部署、负载均衡、健康检查与优雅摘流。
4. 压测基线纳入 CI：P95、错误率、连接池等待、GC。

## 6. 验证建议

```bash
# 只读首页/主题页
wrk -t8 -c200 -d60s http://127.0.0.1:8080/
wrk -t8 -c200 -d60s http://127.0.0.1:8080/t/1

# 登录后接口需携带会话 Cookie
# 观察 /metrics 中的请求量、延迟、错误率与连接池指标
```

重点关注：

- P95/P99 延迟
- 5xx 与 429 比例
- 数据库连接等待
- SQLite `database is locked`
- SSE 连接数与内存
- 通知 Hub 丢弃更新的次数（慢客户端）

## 7. PostgreSQL 实测记录

本地 PostgreSQL 18 已实际跑通：

- 数据库：`goforum_pg`
- 配置：`configs/goforum.postgres.yaml`，服务端口 `18084`
- 启动时 GORM AutoMigrate 全部模块表成功
- 安装向导创建管理员成功
- 登录后台、首页、主题页、用户主页 `/about` 正常
- 创建主题、注册第二用户、举报主题成功
- 审核队列领取并处理为「隐藏」成功
- 处理结果：`review_queue.status=decided`、`topics.status=hidden`
- 发现并修复：`levels.level` 整数主键在 GORM 默认自增下会把 0 级写成 1，并在每次启动重复插入 Lv0。现已改为 `autoIncrement:false`，并在启动时清理历史重复行、校正 0–6 级。

说明：

- PostgreSQL 可作为生产数据库使用。
- 当前压测和容量数据仍需在目标硬件上补充。
- 本地测试使用 trust 认证；生产必须使用密码/TLS 和最小权限账号。

## 8. 当前边界

- 未接入 Redis。
- 未实现多实例 SSE 广播。
- 未实现读写分离。
- 私信列表仍有 N+1 查询。
- 未提供正式压测报告。
- 生产环境建议至少使用 PostgreSQL/MySQL，并在上线前完成压测与容量规划。
