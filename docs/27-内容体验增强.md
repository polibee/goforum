## 2. 编辑器

参考 NodeSeek 的轻量 Markdown 编辑器，不引入富文本编辑器：

- 三个页签：`内容` / `预览` / `对照`
- `内容`：原生 Markdown textarea + 语法工具栏
- `预览`：调用服务端 Markdown 渲染接口
- `对照`：Markdown 源文 + 预览双栏
- 工具栏：粗体、斜体、删除线、标题、引用、代码、链接、图片链接、无序/有序列表、撤销/重做
- 链接/图片使用站内现代化弹窗（非浏览器原生 prompt），支持标题、alt、URL 校验与取消/插入
- 草稿按页面/帖子 ID 存入 localStorage，600ms 防抖
- **正文图片上传按钮已移除**
  - 图片通过“图片链接”按钮或直接粘贴图床 Markdown 插入
  - 例如 `![alt](https://img.example/a.png)`
  - 服务端 goldmark 解析，bluemonday 清洗
- CSP：允许外部 HTTPS 图片（`img-src https:`）

## 3. 通知 SSE

- 登录用户前端自动建立 `EventSource`
- 通知事件写入后通过内存 Hub 立即推送给该用户的 SSE 连接
- 推送负载 `{"unread":n,"latest":{...}}`，顶栏、侧边栏与移动端底部角标同步更新
- 未读数增加时弹出「回复 / @提及 / 点赞 / 私信 · 标题」通知浮层，点击直达目标
- 连接建立时先发送当前未读状态，之后仅由事件驱动；25 秒心跳保活
- 断线由浏览器自动重连

## 4. 投票帖

- 发帖页可展开“添加投票”，填写问题、每行一个选项、是否多选
- 数据表：`polls`、`poll_options`、`poll_votes`（用户+选项唯一）
- 主题页显示选项、票数、百分比进度条
- 单选使用 radio，多选使用 checkbox
- 重新投票会覆盖旧选择
- 显示“已投票 / 投票已结束 / 登录后投票”

## 5. 捐赠 / 打赏

- 个人资料「捐赠设置」：
  - 启用捐赠按钮
  - 捐赠说明
  - 外部捐赠链接（http/https）
- 开启后，主题页标题下方显示「支持作者」横幅，展示头像、捐赠说明和入口
- 第三方平台链接以「前往捐赠」按钮新窗口打开（`noopener noreferrer`）
- 支持积分打赏：5 / 10 / 20 / 50；未配置第三方链接时以积分打赏为主按钮
- 作者查看自己的主题时仍能看到横幅与「编辑捐赠设置」，但不显示积分打赏
- 游客显示「登录后积分打赏」；打赏成功后显示成功提示
- 打赏在同一事务中完成扣款与入账，记录 `tips` 表
- 主题作者的首楼不再重复显示帖子内捐赠入口；其他开启捐赠的回复作者仍保留桌面端入口
- 不能给自己打赏；积分不足会拒绝

## 6. 自定义表情与树状评论

### 表情回复

- 表态接口允许 `emoji:<单个表情>`，拒绝空值与超过 8 个码点的输入。
- 帖子操作区提供表情选择器；选择后写入 `reactions`，页面刷新后以「表情 + 计数」胶囊展示。
- 已选表情可再次点击取消；取消后胶囊隐藏。
- 访客可见计数，登录用户可切换。

### 树状评论

- 子回复按 `reply_to_post_id` 归入父回复，不再平铺。
- 父回复下方显示「N 条回复」`<details>`，默认展开，可折叠。
- 子回复使用独立卡片、缩进与左侧层级容器，保留楼层号、签名、点赞、回复与编辑入口。
- 支持任意层级递归渲染；每层使用相同折叠模板。
- 修复了分组时先拷贝父回复、后追加子回复导致子回复丢失的问题，并补充多级嵌套测试。

## 7. 页脚构建器与分页

### 页脚多列

- `nav_items` 增加 `section` 字段，后台菜单表单提供「页脚分组（可选）」。
- 页脚按 `section` 分组渲染为多列；未设置分组时保持单行页脚。
- 页脚菜单支持权限、外链、排序、启用/停用，全部由后台管理。

### 分页

- 首页/板块/标签：`?page=N`，保留筛选与排序参数。
- 主题：按楼层分页，显示「第 N / M 页」。
- 用户主页：主题/回复标签页各自分页。
- 页码链接由 `pageURL` 保留已有查询参数。

## 8. 后台英文

- `web/locales/en-US/admin.json` 覆盖后台模板全部静态文案与后台导航。
- `admin` 布局的导航、页面标题使用 `t` / `tTitle`，标题后缀（站点名）保持不变。
- 已移除 `/admin` 强制中文逻辑，访问 `/admin?lang=en-US` 可切换英文后台。
- 页面内容（如静态页标题）属于用户数据，不参与翻译。

## 16. 用户搜索

## 17. 后台数据概览

- 仪表盘新增「待处理」KPI：举报、审核队列、申诉的待处理总数，并链接到审核工作台。
- 新增近 14 天新增趋势图：按 UTC 日期分组统计用户、主题、回复，三色柱状展示，柱高按 14 天峰值归一化。

- 图表使用服务端渲染与内联高度，不依赖前端图表库；柱体带 `title` 提示具体数值。新增 Tailwind 类后需执行 `npm run build:css`，并重新编译二进制以更新内嵌静态资源。

## 18. 主题页浏览体验

- 回复支持正序 / 倒序切换：`/t/{number}?sort=desc` 按楼层从新到旧展示，翻页时保留排序与「只看楼主」参数。
- 倒序只影响顶层回复顺序，楼中楼子回复仍挂在父回复下方，避免层级错乱。
- 顶部操作区新增「分享」：支持系统分享面板（`navigator.share`），不支持时复制当前链接并提示，游客也可使用。
- 回到顶部按钮改为滚动超过 600px 后出现，移动端位于底部导航上方，桌面端位于右下角，点击平滑滚动到顶部。
- 登录用户再次进入主题时，在首个未读回复前显示「以下为新回复」分隔线；倒序模式不显示。
- 分页升级为数字页码：显示首页、末页、当前页前后两页，其余用省略号折叠；当前页高亮并带 `aria-current="page"`。
- 主题分页会保留「只看楼主」和倒序参数，翻页后筛选状态不丢失。
- 正序 / 倒序与分享文案已补齐英文翻译。

## 20. 楼层链接与定位

- 楼层号（如 `#3`）点击后复制该楼层的完整链接，并平滑滚动到对应回复。

## 64. 第三方账号登录（Google / GitHub）

- 依赖：`golang.org/x/oauth2`，走标准 Authorization Code 流程，四个参数（ClientID / ClientSecret / RedirectURL / Scopes）即可打通。
- 身份模型：新增 `oauth_identities` 表（`provider + provider_user_id` 唯一），一个本地账号可绑定多个平台，一个平台账号只能对应一个本地账号。
- 登录流程：
  - `/oauth/:provider` 生成随机 nonce，写入 `HttpOnly` + `SameSite=Lax` 的 10 分钟 state cookie，再跳转授权页。
  - `/oauth/:provider/callback` 校验 state 与 provider 一致，交换 token，拉取用户资料并登录。
  - 首次登录：已有绑定 → 直接登录；邮箱已验证且与本站账号一致 → 自动绑定并登录（可关闭）；否则按站点注册策略创建账号（`closed` 拒绝、`approval` 进入待审）。
  - 第三方邮箱视为已验证，创建账号时写入 `email_verified_at`。
  - 用户名从昵称/邮箱前缀推导，非法字符替换，重名自动加后缀。
- 账号绑定：
  - 账号安全页新增「第三方账号」卡片，展示每个平台的绑定状态、平台用户名与邮箱。
  - `?link=1` 发起绑定，回调后跳到账号安全页；`POST /settings/security/oauth/:provider/unlink` 解绑。
  - 拒绝解绑最后一个登录方式（无密码且仅剩一个绑定）。
- 后台「登录方式」页（`/admin/auth`，权限 `settings.integration`，位于「用户」分组）：
  - 每个平台一张卡片：启用开关、Client ID、Client Secret（掩码存储、回显为空、留空保持不变）、回调地址（可一键复制，默认自动生成）、Scopes（留空用默认）。
  - 状态徽章三态：运行中（已启用且密钥完整）/ 待补全（启用但缺密钥）/ 未启用。
  - 全局选项：邮箱一致时自动绑定、隐藏账号密码表单（仅第三方登录）。
  - 保存前校验：启用时必须同时具备 Client ID 与 Secret；自定义回调地址必须与本站同域。
  - 保存写入审计（`settings.oauth.update`，密钥记为 `***`）。
  - 每张卡片附官方控制台入口（Google Cloud Console / GitHub Developer Settings）。
- 登录与注册页在启用后自动展示对应平台按钮（内联 SVG 图标，无外部请求，符合 CSP），未启用任何平台时不显示分隔线。

## 65. Laravel 风格 .env 配置

- 新增配置文件 `.env`（项目根目录，格式与 Laravel 一致），作为数据库等基础配置的**唯一推荐填写位置**。
- 解析器 `internal/platform/config/dotenv.go`：
  - 支持 `KEY=VALUE`、`export KEY=VALUE`、`#` 注释、单/双引号、`${VAR}` 引用前面的变量。
  - 未加引号的值自动去掉行尾 ` # 注释`；文件缺失不报错（回落到默认值）。
  - 文件位置可用 `GF_ENV_FILE` 指定，默认 `./.env`。
- 加载优先级（后者覆盖前者）：
  `内置默认值 → configs/goforum.yaml → .env → 真实环境变量`
  - `.env` 高于 YAML，因此只改 `.env` 即可切换数据库，不需要动 YAML。
  - 真实环境变量仍最高，方便容器与 CI 覆盖。
- 数据库按 Laravel 习惯拆成独立字段，由程序自动拼接 DSN：
  - `DB_CONNECTION=sqlite|mysql|pgsql`
  - SQLite：只填 `DB_DATABASE=./data/goforum.db`
  - PostgreSQL：`DB_HOST`、`DB_PORT`（默认 5432）、`DB_DATABASE`、`DB_USERNAME`、`DB_PASSWORD`、`DB_SSLMODE`（默认 disable）
  - MySQL：`DB_HOST`、`DB_PORT`（默认 3306）、`DB_DATABASE`、`DB_USERNAME`、`DB_PASSWORD`
  - 驱动别名兼容：`pgsql|postgres|postgresql`、`mariadb|mysql`、`sqlite3|sqlite`
  - 高级用法 `DB_DSN` 优先于分项字段。
- 其余键名对齐 Laravel：`APP_ENV`、`APP_URL`、`APP_KEY`、`CACHE_STORE`、`REDIS_URL`、`FILESYSTEM_DISK`、`STORAGE_PATH`、`MAIL_MAILER`、`MAIL_HOST`、`MAIL_PORT`、`MAIL_USERNAME`、`MAIL_PASSWORD`、`MAIL_FROM_ADDRESS`、`LOG_LEVEL`、`LOG_CHANNEL`、`SESSION_COOKIE`、`SESSION_LIFETIME`、`WORKER_ENABLED`。
- 时长写法兼容两种：`720h` / `30m`，以及纯数字按秒（`SESSION_LIFETIME=1209600`）。
- 新增 `.env.example`：带分组注释与三种数据库的填写模板，复制为 `.env` 即可使用。
- 启动日志会打印生效来源与数据库，便于确认配置是否被读取：
  `"env_file":".env","db":"postgres/goforum_pg"`。
- 后台「系统信息」页新增只读「运行配置」区块：展示 `.env` 路径与加载状态、以及 `APP_ENV`/`DB_CONNECTION`/`DB_DATABASE`/`CACHE_STORE`/`MAIL_MAILER` 等当前生效值，并提示「修改 .env 后重启」。不提供网页内编辑，避免与文件配置产生双写歧义。
- `configs/goforum.example.yaml` 补充优先级说明，注明数据库推荐写在 `.env`。
- `.env` 已在 `.gitignore` 中，不会被提交。
- 数据库三种接法以**整块区块**形式并列写入 `.env`，每块自带 `DB_CONNECTION`：
  - 当前使用的区块取消注释，另外两块整体加 `#` 注释。
  - 切换数据库时只需给旧区块加注释、给新区块去注释，不必逐行改动，也不会残留旧的主机/密码。
  - 已验证：注释掉 PostgreSQL 区块后，其 `DB_HOST`/`DB_PORT`/`DB_USERNAME` 等键完全不出现在解析结果里，不会被误读取。

## 72. Redis 缓存与高并发支持

### 之前的状态
缓存包 `internal/platform/cache` 是**死代码**（零调用方），限流是纯进程内 map，后台任务无选主，站点统计每次渲染跑 3 次 `COUNT(*)`。配置里有 `cache.driver`/`redis_url`，但从未用来创建实例——多实例部署不可行。

### 缓存抽象
重写 `Cache` 接口，内存与 Redis 两个驱动实现同一契约：

| 方法 | 用途 |
|---|---|
| `Get` / `Set` / `Delete` | 通用键值 |
| `Incr(key, delta, ttl)` | 原子自增，限流与计数器 |
| `Expire` | 重置 TTL |
| `Add(key, val, ttl)` | set-if-absent，作为分布式锁 |
| `DeletePrefix` | 按前缀失效一族键 |
| `Driver` / `Close` | 运维观测与释放连接 |

- `Open(ctx, driver, url, prefix, ttl)` 统一构造：空/`memory` → 进程内；`redis` → 需可连通（启动时 Ping，失败即启动失败，不静默降级）。
- 修掉了内存驱动的一个旧缺陷：`Incr` 原来把字符串按字节当十进制解析，非数字 key 会产生垃圾值；现在非数字一律重置为 delta。

### Redis 驱动
- 基于 `github.com/redis/go-redis/v9`，`redis.ParseURL` 支持 `redis://user:pass@host:port/db`。
- `Incr` 用 `INCRBY` + `EXPIRE NX` 流水线，跨进程原子。
- `Add` 用 `SET NX`，天然是分布式锁。
- `DeletePrefix` 用 `SCAN` 游标遍历而非 `KEYS`，避免阻塞 Redis。
- 支持 `CACHE_PREFIX`，一个 Redis 可服务多个站点；已用测试验证前缀隔离。

### 接入点
1. **限流**：`RateLimit` 改为走缓存。Redis 下每个 IP 的限额在所有实例间共享，反向代理后不会因负载均衡被放大。缓存故障时**失败开放**（放行而不是拦下全部用户）。
2. **站点统计**：`SiteStats`（用户/主题/回复数）从每页 3 次 `COUNT(*)` 改为缓存 60 秒，写操作后失效。
3. **后台任务选主**：`StartBackground` 在 Redis 下用 `Add` 抢租约，每小时重算信任等级只由一个实例执行；Deipay 5 秒轮询同样加锁，避免多实例重复下单。
4. **设置跨实例生效**：`SetMany` 成功后递增 `settings:version`，其他实例每 15 秒检查一次并在变化时重载。之前多实例下改设置只有当前进程能看到。
5. **WORKER_ENABLED 生效**：之前该配置只用于界面展示，现在真正控制后台任务是否启动。

### 配置
```dotenv
CACHE_STORE=memory        # memory | redis
REDIS_URL=                # redis://:password@127.0.0.1:6379/0
CACHE_PREFIX=goforum:     # 多站点共用一个 Redis 时隔离
CACHE_TTL=5m
```
切换只需改 `CACHE_STORE=redis` 并填 `REDIS_URL`，重启生效。后台「系统信息」页显示当前驱动、前缀，并用一句话说明该配置对扩容的影响。

### 验证
- 13 个缓存测试覆盖：契约一致性、并发自增原子性（50 goroutine / 5 客户端）、非数字值处理、过期、前缀隔离、多个客户端抢锁只有一个成功、Redis 不可达时报错而非挂起。
- 用 `miniredis` 起了真实 Redis 协议服务，把 `CACHE_STORE` 切到 `redis` 跑完整应用，确认写入的键：
  - `goforum:stats:site = {"Users":2,"Topics":3,"Posts":6}` — 站点统计
  - `goforum:job:deipay-poll = 1` — 后台任务锁
  - `goforum:rl:127.0.0.1|search = 5` — 限流计数
- 服务在 Redis 后端下正常启动，日志零 ERROR。
- `go vet` 与 `go test ./...` 全通过（25 个包）。

### 仍未解决的多实例问题
- **SSE 通知**仍是进程内连接表（`notification/hub.go`），一个实例只能推送给连到自己的客户端。
- **事件总线**仍是进程内 MemoryBus，跨实例事件不会传播（如 A 实例下单、B 实例的缓存失效）。
- 备份加密与 2FA 当时仍未实现（2FA 已于 2026-11-10 补齐，见 `32-管理员TOTP两步验证.md`）。

这些已列入后续项。当前 Redis 缓存解决了限流、计数器、任务选主、设置同步四个最影响多实例正确性的问题。

## 73. 事件总线与 SSE 跨实例广播

上一节解决了限流、计数器、任务锁、设置同步；这一节补齐多实例部署最后两块：事件总线和 SSE 推送。

### 事件总线（`internal/platform/events/redis.go`）

新增 `RediBus` 包装现有的 `MemoryBus`：

- **发布**：先执行本进程的 handler（保持原有的同步语义与错误处理），再把事件 JSON 发到 Redis 频道 `events:broadcast`。
- **订阅**：后台 goroutine 接收其他实例的事件，交给本地 `MemoryBus` 分发。
- **防重复**：发布时记录事件 ID（30 分钟窗口），收到自己的 Redis 回声时跳过，避免同一实例执行两次 handler。
- **失败降级**：Redis 连不上时启动日志告警，自动退回纯内存总线，站点仍能工作，只是跨实例事件不传播。
- **构造即验证**：`NewRedisBus` 启动时 Ping 并确认订阅建立，配置错误在启动阶段暴露而不是静默丢事件。

效果：A 实例发帖产生的 `topic.replied` 事件，B 实例注册的处理器（通知、积分等）也会执行。

### SSE 推送（`internal/modules/notification/hub.go`）

`hub` 增加 Redis 模式：

- 本地连接表保持不变，`publish` 先投递给本进程的 SSE 客户端，再发布到频道 `sse:notify`。
- 其他实例收到后按 `user_id` 投递给连在自己身上的浏览器。
- 用 `origin`（实例 ID）过滤掉自己的广播，本地不会收到重复推送。
- 浏览器连接到 A、通知产生于 B，用户仍能即时收到——这是之前完全做不到的。
- 发布使用 `context.Background()`，避免请求结束取消广播。

### 装配

- `Cache` 接口新增 `RedisClient()`，把缓存持有的连接暴露给事件总线与 SSE hub，**三者共用一个连接池**。
- `App` 结构区分 `Bus`（可能是 RediBus）与 `LocalBus`（始终是 MemoryBus），订阅注册走的仍是 `Bus` 接口，模块层无需感知差异。
- 关闭顺序：先停 SSE 订阅 → 停事件总线订阅 → 关缓存客户端 → 关数据库，避免向已关闭的连接写数据。

### 验证

**单元测试（26 个包全通过）**
- 事件总线：跨实例投递、本地不重复执行、内存总线回归、nil client 报错。
- SSE：跨实例推送、本地不重复、用户间隔离（alice 的推送不会到 bob）、纯本地模式、nil client 报错。

**端到端双实例验证**
用 `miniredis` 起 Redis，同时跑两个应用实例（18085 / 18086），共享同一 Redis：

```
active channels: [events:broadcast sse:notify]     ← 两个实例都已订阅
goforum:job:deipay-poll = 1                        ← 任务锁，轮询串行不重复
```

- 在实例 A 修改站点设置 → Redis 里 `goforum:settings:version` 从无到 `1`
- 等待一个检查周期后，**实例 B 日志出现 `settings reloaded from another instance`**，说明跨实例配置同步生效

### 多实例部署现在具备的能力

| 能力 | 状态 |
|---|---|
| 限流跨实例共享 | ✅ Redis |
| 站点统计缓存共享 | ✅ Redis |
| 后台任务选主（不重复执行） | ✅ Redis 租约 |
| 设置变更跨实例生效 | ✅ 版本号 + 15s 轮询 |
| 事件跨实例传播 | ✅ Redis Pub/Sub |
| SSE 推送跨实例到达 | ✅ Redis Pub/Sub |
| 会话共享 | ✅ 数据库存储（原本就支持） |
| 文件上传共享 | ⚠️ 需共享存储（NFS/S3），本地磁盘不支持 |

当时仍未解决：备份加密、2FA（2FA 已于 2026-11-10 补齐，见 32 文档）。文件上传若要多实例部署需改用对象存储。

## 74. 并发压测与单实例容量结论

### 压测中发现并修复的致命缺陷

第一次压测（20 并发）时进程直接崩溃，日志为 `fatal error: concurrent map read and map write`：

- 位置：`internal/platform/view/view.go` 的模板缓存 `r.cache`。
- 原因：`Render` 每个请求读这个 map，而首次未命中和开发模式下会写入，未加锁。任何并发量下都可能触发 Go 运行时的 map 竞态检测并**终止进程**。
- 影响：这是生产级致命 bug，普通流量下也可能偶发崩溃。
- 修复：`Renderer` 增加 `sync.RWMutex`，读走 `RLock`，编译走 `Lock` 并对同名页面做双重检查，避免重复解析。

修复后同样的压测不再崩溃。

### 顺带优化
- `TrendingTopics`（首页侧边「本周热门」）每次请求都执行一个带表达式排序的 7 天范围查询，无法走索引。改为缓存 2 分钟，发帖/回复时按前缀失效。
- 效果：50 并发吞吐从 750 提升到 **810 req/s**，p95 从 72ms 降到 70ms。

### 实测数据

环境：单实例、16 逻辑核、内存缓存、本地磁盘。

| 场景 | 并发 | 吞吐 | p50 | p95 | p99 | 5xx |
|---|---|---|---|---|---|---|
| 首页（SQLite） | 20 | 711 req/s | 26ms | 33ms | 37ms | 0 |
| 首页（SQLite） | 50 | 810 req/s | 61ms | 70ms | 74ms | 0 |
| 首页（SQLite） | 100 | 771 req/s | 129ms | 137ms | 144ms | 0 |
| 首页（SQLite） | 200 | 817 req/s | 247ms | 260ms | 266ms | 0 |
| 主题页（写浏览数） | 30 | 499 req/s | 59ms | 64ms | 69ms | 0 |
| 首页（PostgreSQL） | 50 | 729 req/s | 67ms | 78ms | 89ms | 0 |

关键结论：

1. **吞吐在 800 req/s 附近饱和**，并发从 50 加到 200 吞吐几乎不变，延迟线性上升（排队）。说明瓶颈不是崩溃或锁竞争，而是单进程的渲染能力。
2. **SQLite 与 PostgreSQL 表现接近**（810 vs 729），说明瓶颈不在数据库，而在 Go 层的模板渲染与业务逻辑。
3. **全部压测零 5xx、无进程退出**，连接错误数与并发数相同（客户端连接池上限），属压测工具侧现象。

### 单实例能承载多少真实用户

`req/s` 不等于用户数。一个论坛用户的实际行为：

- 浏览一页 = 1 次 HTML 请求 + 若干静态资源（静态资源走缓存，不进业务逻辑）
- 停留时间通常 10–30 秒

按 800 req/s 与每人每分钟 3 次页面浏览估算：

- **理论并发在线**：约 3000–4000 人同时在线浏览
- **保守建议**：单实例支撑 **日活 1 万以内、同时在线 500–1500** 的社区比较稳（保留 2–3 倍余量应对突发）

主题页（有写库）499 req/s 是更保守的参考值：若站点以读帖为主，按 500 req/s 折算，同时在线 1000 人左右仍有明显余量。

### 单实例部署是否可行

**可行**，且这是当前推荐的默认形态：

- 会话存在数据库，重启不掉登录
- 缓存、限流、任务锁在单进程内自洽，不需要 Redis
- 后台任务只有一个实例，不会重复执行
- 文件上传存本地磁盘即可，无需对象存储

需要 Redis 和多实例的临界点是：

- 需要横向扩容（单机 CPU 打满且无法再优化）
- 需要高可用（单点故障不可接受）
- 同时在线稳定超过 2000 人

## 75. PostgreSQL 单实例压测与写操作并发验证

### 压测中发现并修复的 PostgreSQL 专属严重缺陷

写操作压测第一轮，**所有回复在 PostgreSQL 下全部失败**：

```
错误: 字段关联 "highest_post_number" 是不明确的 (SQLSTATE 42702)
```

- 位置：`internal/modules/community/service.go` 的两处 `ON CONFLICT ... DO UPDATE`（发表回复、标记已读）。
- 原因：`gorm.Expr("CASE WHEN highest_post_number < ? THEN ? ELSE highest_post_number END")` 里的列名没有限定。在 `INSERT ... ON CONFLICT DO UPDATE` 语句中，PostgreSQL 无法判断这个列指「已存在的行」还是「待插入的行」，直接报歧义错误。
- 影响：**PostgreSQL 部署下回复功能完全不可用**，标记已读也失败。SQLite 与 MySQL 对此较宽松，所以之前完全没暴露。
- 修复：表达式里的列名加表名限定 `topic_users.highest_post_number`。

这是本次压测最有价值的产出——如果不做写路径压测，直到用户第一次回复才会发现。

### 写操作并发正确性验证

压测程序直接调用服务层（绕过 HTTP 限流，限流本身是正确行为会掩盖真实事务逻辑），在真实 PostgreSQL 上验证：

| 场景 | 并发 | 成功 | 失败 | 一致性检查 |
|---|---|---|---|---|
| 发回复 | 16 | 160 | 0 | reply_count 总和 = 写入数；post_count = reply_count+1（16/16 主题） |
| 发回复 | 32 | 480 | 0 | 同上，480 = 480 精确匹配 |
| 发回复 | 64 | 1280 | 0 | 同上，1280 = 1280 精确匹配 |
| 点赞/取消（成对） | 64 | 2560 | 0 | like_count 归零，reactions 无残留行 |
| 发主题 | 64 | 320 | 0 | 分类计数增长（217–253 次/秒） |

关键验证点全部通过：

- **帖号无重复**：`GROUP BY (topic_id, post_number) HAVING COUNT(*) > 1` 结果为空，说明 `post_count` 上的 CAS 乐观锁在并发下有效
- **计数器精确**：`reply_count` 总和与成功写入数完全相等，没有丢失或重复计数
- **`post_count = reply_count + 1`**：全部主题成立（+1 是首帖）
- **点赞幂等**：成对 toggle 后 `like_count` 精确归零，`reactions` 表无残留，说明唯一索引与删除逻辑一致

### 两类数据库的 HTTP 读压测对比

同一台机器、同样 15 秒、同样的首页路径：

| 并发 | PostgreSQL | SQLite |
|---|---|---|
| 20 | 617 req/s, p95 33ms | 753 req/s, p95 28ms |
| 50 | 622 req/s, p95 85ms | 746 req/s, p95 72ms |
| 100 | 627 req/s, p95 171ms | 730 req/s, p95 155ms |

**SQLite 反而略快**（约 15–18%），原因：

1. SQLite 是进程内调用，没有网络往返；PostgreSQL 每条查询都要走 TCP
2. 首页读多写少，SQLite 的 WAL 模式读并发表现很好
3. 两个数据库都是零 5xx、无崩溃

这说明**读性能瓶颈不在数据库**，而在模板渲染与业务逻辑。选型时数据库的决定因素应是并发写入、数据规模和运维需求，而不是读吞吐。

### PostgreSQL 与 SQLite 如何选择

| 维度 | SQLite | PostgreSQL |
|---|---|---|
| 读吞吐（单实例） | 730–753 req/s | 617–627 req/s |
| 并发写入 | 单写者（WAL），写多会排队 | 多写者，明显更好 |
| 数据规模 | 建议 < 10GB | 无实际上限 |
| 备份/恢复 | 复制文件 | pg_dump / PITR |
| 多实例部署 | 不适合（文件锁） | 天然支持 |
| 运维成本 | 零 | 需维护服务 |

**建议**：

- 日活 1 万以内、以读为主、单实例 → **SQLite 完全够用**，且更省心
- 有较多并发写入（大量回复/点赞）、数据超 10GB、需要高可用或多实例 → **PostgreSQL**

### 压测方法与局限

- 写操作压测使用临时 Go 程序直接调服务层（已删除），生成临时用户/主题/分类，跑完用 SQL 独立校验计数器，而不是只信程序返回值。
- 局限性：单机压测（压测客户端与服务同机，互相抢 CPU）；未覆盖 HTTP 全链路（中间件、CSRF、限流）；未测长连接 SSE 在压测下的表现。
- 建议上线前在目标服务器、用生产配置（HTTPS + 反向代理 + 真实数据量）复跑。

## 76. MySQL 单实例压测与第二个方言缺陷

### 压测中发现并修复的 MySQL 专属致命缺陷

MySQL 首页压测第一轮出现 **1.2 万次 5xx**，日志为：

```
list topics failed: sql: Scan error on column index 15, name "last_posted_at":
unsupported Scan, storing driver.Value type []uint8 into type *time.Time
```

- 原因：MySQL 驱动默认把 `DATETIME` 读成 `[]byte`，必须显式带 `parseTime=true` 才能映射到 `time.Time`。
- 触发路径：安装器会把提交的 DSN **原样**写进 `configs/goforum.yaml`。手工粘贴 DSN 时很容易漏掉 `parseTime`（例如在 shell 里 `&parseTime=True` 的 `&` 会被当成后台运算符而截断）。
- 影响：**漏掉该参数时首页直接打不开**，所有涉及时间列的查询全部失败。
- 修复：在驱动层强制补齐参数，不依赖用户输入：

```go
func ensureMySQLParams(dsn string) string {
    // 强制 parseTime=true、charset=utf8mb4、loc=UTC，
    // 已有的值保持不变，其他参数原样保留
}
```

已加单元测试覆盖「缺失时补齐」「已有值保留」「保留无关参数」三种情况。

| 发回复 | 1280 | 0 | reply_count = 1280 精确；post_count=reply_count+1 全部成立 |
| 帖号重复检查 | — | — | 0 重复，CAS 乐观锁有效 |
| 点赞/取消（成对） | 2560 | 0 | like_count 归零，reactions 无残留 |

发回复 445 次/秒，点赞 2633 次/秒。

### 三数据库 HTTP 读压测对比

同一台机器、15 秒、首页路径：

| 并发 | SQLite | PostgreSQL | MySQL |
|---|---|---|---|
| 20 | 753 | 617 | 637 |
| 50 | 746 | 622 | 639 |

### 三轮压测累计发现的方言缺陷

| 数据库 | 缺陷 | 严重程度 |
|---|---|---|
| 三者共通 | 模板缓存 map 无锁，并发下进程崩溃 | 致命 |
| PostgreSQL | `ON CONFLICT` 中列名歧义，**回复完全不可用** | 致命 |
| MySQL | DSN 缺 `parseTime` 时**首页完全打不开** | 致命 |

这三个问题在开发环境的 SQLite 单线程访问下都不会暴露，只有换数据库 + 并发访问才能发现。**建议任何换库上线前，先跑一遍本节的压测流程。**

### 当前仍可优化的点（按收益排序）

1. **`trust_level` 重算仍是全表扫描 + N+1**
   `RecomputeTrustLevels` 把所有 `trust_level < 4` 的活跃用户读进内存，再逐个查 3 次聚合。1 万用户 = 每小时 3 万次查询。建议改为单条 `GROUP BY` 聚合，只回写变化的行。

2. **`ReindexSearch` 全量加载**
   管理员点一次「重建索引」会把所有主题和回复读进内存（含 `raw` 大字段），无分批无进度。数据量大时可能 OOM。建议按 ID 游标分批（1000/批）并异步执行。

3. **书签页、审核队列页仍有 N+1**
   每行 1–3 次查询，20 条/页最多 60–80 次。改为 `WHERE id IN (...)` 批量取。

4. **`ads.Price` 等少数查询用 `context.Background()`**
   脱离请求取消，慢查询无法中断。

5. **未处理错误的写操作仍有 10 处**
   多为非关键路径（更新最后活跃时间等），但严格来说应该记录日志。

6. **SQLite 未启用外键约束**
   删除用户/主题后可能留孤儿行，建议加对账清理任务。

7. **邮件发送无超时与重试**
   `smtp.SendMail` 在 goroutine 里，超时后 goroutine 仍挂着；发送失败仅丢弃。

8. **备份不加密**，且 `pg_dump` 把密码放在命令行参数里（同机其他用户 `ps` 可见）。

9. 当时未实现 2FA，超管仅密码单因子（已于 2026-11-10 补齐，见 32 文档）。

10. **文件上传本地磁盘**，多实例部署需改对象存储。

以上 1–3 是性能项，4–9 是安全/运维项。当前单实例、日活 1 万以内的场景下，这些不构成阻塞；若要支撑更大规模或对外提供服务，建议按顺序处理。

## 77. 性能与运维优化落地

上一节列出的优化点，本轮完成 6 项。

### 1. 信任等级重算：从 3N 次查询降为固定次数

**问题**：`RecomputeTrustLevels` 每小时执行，把全部 `trust_level < 4` 的活跃用户读进内存，然后对每个用户调用 3 次 `COUNT`。1 万用户 = 3 万次查询。

**修复**：
- `contracts.ActivityReader` 新增 `UserActivityBatch(ctx, userIDs)`。
- community 实现为 3 条分组聚合查询（按 500 用户分块），一次返回所有用户的 topic/post/like 计数。
- `RecomputeTrustLevels` 改为先批量取计数，再逐个计算等级。

**效果**：查询数从 `3N + 1` 降到 `3 × ceil(N/500) + 1 + 变更数`。1 万用户时从 3 万次降到约 61 次（不含实际变更的 update）。

**验证**：`UserActivityBatch` 返回的 topics/posts/likes 与实际数据一致（topics=3, posts=6, likes=1）。

### 2. 搜索索引重建：改为游标分批

**问题**：`ReindexSearch` 用 `Find(&topics)` 和 `Find(&posts)` 全量加载（含 `raw` 大字段），且每个 topic 再查首帖、每个 post 再查所属主题 —— 双层 N+1。数据量大时可能 OOM。

**修复**：
- 按 `id > lastID ORDER BY id LIMIT 500` 游标分批遍历。
- 主题批次用一次 `WHERE topic_id IN (...)` 取所有首帖。
- 帖子批次用一次 `WHERE id IN (...)` 取父主题。
- 内存占用从「全表」降为「500 行 + 其父主题」。

### 3. 书签页与审核队列：消除 N+1

**书签页**（原来每行 1–2 次查询）：
- `contracts.Reader` 新增 `TopicMetaBatch` / `PostMetaBatch`。
- `ListBookmarks` 先按类型收集 ID，再两次批量查询，最后组装。20 条/页从最多 40 次查询降为固定 2 次。

**审核队列**（原来每行 3 次查询）：
- 新增 `batchTargetTitles`（批量取标题与作者）与 `flagBatch`（一次分组计数 + 一次取最近 flag）。
- 20 条/页从最多 80 次查询降为固定 4 次。

### 4. 支付订单状态更新失败记录日志

`gateway.Create` 失败后把订单标记为 `failed` 的操作原本忽略错误。现在失败会写 `Warn` 日志（订单会停在 pending，需要运维可见）。

### 5. SMTP 发送加硬超时

**问题**：`smtp.SendMail` 在 goroutine 里执行，`ctx` 超时后 goroutine 与 socket 仍挂在后台，服务器无响应时会持续泄漏。

**修复**：
- 自行实现 STARTTLS 发送流程（`sendStartTLS`），dialer 带 `Deadline`，连接建立后 `SetDeadline` 限制整个会话。
- 隐式 TLS（465 端口）路径同样加 deadline。
- 超时上限 30 秒，且不超过调用方 ctx 的 deadline。

### 6. 孤儿数据清理命令

**问题**：模型未声明外键（迁移需兼容三种方言），删除用户或主题后可能留下孤立行。

**新增**：`goforum cleanup [-n]`

```
goforum cleanup -n   # 只统计，不删除
goforum cleanup      # 执行清理
```

覆盖 10 类清理：无父主题的回复、无分类的主题、无目标的反响/收藏、无用户的关注/会话/通知/OAuth 绑定、无用户组的成员、过期会话。

已验证 dry-run 输出正常（当前库 0 孤儿行）。

### 测试适配
新增的批量方法需要更新测试桩：`fakeActivity`、engagement/moderation/gamification 的 `fakeContent` 各补两个方法。修正了一处桩数据不一致（`PostMetaBatch` 的标题需与 `PostMeta` 一致）。

## 78. 备份加密与剩余安全项

### 1. 备份默认加密（AES-256-GCM）

**问题**：备份目录包含完整数据库——密码哈希、第三方支付/OAuth 密钥、全部私信。之前只有目录权限 0700 保护，备份文件本身是明文，一旦被复制走就是完整数据泄露。

**实现**（`internal/platform/backup/encrypt.go`）：
- 每个备份文件独立加密，布局为 `GFBK1` 魔数 + 12 字节随机 nonce + 分块密文。
- 64KB 分块，每块 nonce 由基础 nonce 与序号异或派生，保证同一密钥下 nonce 不复用。
- 每块带 GCM 认证标签，篡改任意字节都会导致解密失败。
- 加密后**删除原明文文件**，目录里不留未加密副本。

**密钥管理**：
- 从 `GF_BACKUP_KEY` 读取，或命令行传入。
- 未配置密钥时**拒绝执行备份**，除非显式传 `-plaintext`。静默写明文等于没有加密。
- `goforum backup -gen-key` 生成随机 32 字节密钥。

**恢复**：
- 新增 `goforum restore -o FILE BACKUP_FILE`，解密后再交给数据库工具导入。
- 不直接写入数据目录，避免误覆盖运行中的库。

**验证**：
- 9 个测试覆盖：往返一致性、多分块、错误密钥失败、篡改检测、密钥必填、明文允许、密钥随机性、两次加密输出不同（nonce 随机）。
- 端到端实测：`backup` 生成的 `database.db` 文件头为 `GFBK1`（不是 `SQLite format 3`），manifest 标记 `encrypted: true`；`restore` 解密后恢复为合法 SQLite 文件。
- 无密钥时命令正确拒绝并给出可操作提示。

### 2. pg_dump 密码不再出现在命令行

**问题**：`pg_dump --dbname=<完整 DSN>` 会把包含密码的连接串放进进程 argv，同机任何用户 `ps` 可见。

**修复**：拆分 DSN 为 host/port/user/dbname 分项参数，密码通过 `PGPASSWORD` 环境变量传递，`sslmode` 通过 `PGSSLMODE`。MySQL 侧原本已用 `MYSQL_PWD`，保持不变。

### 3. 剩余写操作错误处理

逐个评估后只改有两处业务影响的：

- **`CreateAdmin` 写 `email_verified_at`**：原本忽略错误。若失败，开启邮箱验证时管理员将无法登录。改为返回错误。
- **`PointBalance` 并发建行**：原本 `First` 未命中后 `Create` 并忽略错误，并发时唯一索引冲突会返回零值余额（用户看到积分 0）。改为 `ON CONFLICT DO NOTHING` 后重新读取，保证拿到已存在的行。

其余三处（广告点击数、最后活跃时间）保持忽略——失败不影响业务，且这些字段在每次请求中都会重试写入。
