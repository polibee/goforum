# 版主与审核实现

## 1. 已实现能力

### 举报

- 用户可举报主题、回复、私信。
- 入口：主题页「举报」、回复操作、私信消息下方。
- 表 `flags`：举报人、目标类型/ID、原因代码、补充说明、处理状态、处理人、处理时间。
- 同一用户对同一目标重复举报会被唯一索引去重。
- 达到站点设置 `moderation.auto_hide_flags` 阈值时自动隐藏主题/回复。
- 举报写入审核队列 `review_queue`，同目标只保留一个待处理项。

### 审核队列

- 后台 `/admin/review`，权限 `moderation.queue.view`。
- 状态：待处理、未领取、已领取、已处理。
- 支持筛选、分页、优先级（按举报数）。
- 审核项显示目标标题、作者、举报数量、举报原因与说明。
- 版主可「领取」任务，使用 CAS 更新避免多人重复领取。
- 处理动作：
  - 驳回举报
  - 隐藏内容
  - 删除内容
  - 恢复/通过
  - 禁言作者（`suspended`），可选 1 / 7 / 30 天或永久
  - 封禁作者（`banned`），可选 1 / 7 / 30 天或永久
- 处理结果写回 `review_queue` 与 `flags`，并写入审计日志。
- 内容作者收到审核处理通知，举报人收到举报结果通知。
- 后台主题与回复列表均支持批量操作。

### 敏感词

- 后台 `/admin/banned-words`，权限 `moderation.word.manage`。
- 支持包含、精确、正则三种匹配。
- 动作：拦截、转审核。
- 发帖/回复前由 `ContentGuard` 检查。

### 权限与用户组

- 权限键：
  - `flag.create` 举报
  - `flag.review` 处理举报
  - `moderation.queue.view` 查看队列
  - `moderation.action` 执行审核动作
  - `moderation.word.manage` 管理敏感词
  - `moderation.audit.view` 查看审计
- 版主通过用户组授予上述权限；后台用户组页面可配置。
- 超级管理员与具备权限的用户组可进入审核队列。

### 用户状态

- `active` 正常
- `suspended` 禁言，可带到期时间
- `banned` 封禁，可带到期时间
- `rejected` 拒绝
- `pending_review` 待审核

登录与鉴权会拒绝非 `active` 账号。禁言/封禁到期后，下一次身份读取会自动恢复为 `active` 并清空到期时间。受限账号即使保留旧会话，访问需要登录的页面也会被清除会话并跳转登录页。

## 2. 版主如何进入后台

后台不是只给超级管理员开放，而是按权限开放：

1. 启动时自动创建「版主」用户组（slug `moderators`），默认权限：
   - `admin.access` 进入后台
   - `admin.content.view` 查看内容管理
   - `topic.moderate` 管理主题（锁定、删除等）
   - `topic.pin` 置顶 / 取消置顶
   - `topic.feature` 设置 / 取消精华
   - `flag.review` 处理举报
   - `moderation.queue.view` 查看审核队列
   - `moderation.action` 执行审核动作
2. 超级管理员在「后台 → 用户组」中把用户加入该组，或在用户详情页分配用户组。
3. 版主登录后：
   - 账号菜单出现「审核队列」入口；
   - 直接访问 `/admin/review`；
   - 访问 `/admin` 会自动跳转到审核队列；
   - 仅能访问被授权的页面；`/admin/users`、`/admin/settings`、`/admin/modules` 等未授权页面返回 403。
4. 不授予 `admin.access` 的用户即使有审核权限也无法进入后台；这是当前权限模型的设计。

## 3. 账号申诉

- 登录页提供「账号被限制？提交申诉」入口。
- 公开路由 `/appeal`：输入用户名和申诉说明，无需登录。
- 仅允许 `suspended` / `banned` 账号创建待处理申诉；不存在的用户返回同样的成功页面，避免账号枚举。
- 同一用户只保留一个待处理申诉。
- 后台 `/admin/appeals`：
  - 按待处理 / 已通过 / 已拒绝筛选；
  - 通过并解封：账号恢复 `active`，清空到期时间；
  - 拒绝：保留限制状态，可填写备注。
- 申诉处理写入审计日志。
- 申诉结果通过「申诉结果」通知发送给用户；通过时链接首页，拒绝时链接申诉页。
- 公开提交按 IP 限流 5 次/小时。

## 4. 审计

- 举报创建、领取、处理、敏感词变更均写审计日志。
- 管理动作记录操作人、目标、原因与 request_id（由审计模块统一处理）。

## 5. 已修复/增强

- 审核队列现在直接展示举报原因代码和补充说明，不再只显示举报次数。
- 审核处理支持恢复/通过、隐藏、删除、禁言、封禁；禁言/封禁支持期限。
- 审核结果通过通知事件发送给内容作者，通知类型为「审核处理」，并带处理动作与直达链接。
- 目标内容被隐藏/删除后通过现有内容服务同步更新状态。

## 6. 当前边界

- 已支持限时禁言/封禁与自动解除；永久状态仍可选。
- 申诉流程已实现，申诉结果会发送站内通知；暂不支持撤回申诉。
- 审核结果已通知内容作者；举报人会收到「举报结果」通知。
- 审核队列顶部显示待领取、处理中、今日已处理统计。
- 私信举报的处理动作目前仅结案，不单独删除会话消息。
- 已有队列状态统计；尚无按版主维度的处理量、平均处理时长与举报趋势报表。
- 审核队列未提供按版主/时间/原因筛选。
- 版主权限依赖用户组配置，未提供一键「版主」角色模板。

## 7. 测试

- 单元测试覆盖举报、审核队列、领取、处理动作与敏感词。
- PostgreSQL 环境实测：
  1. 安装向导创建管理员；
  2. 创建主题；
  3. 第二用户注册并激活；
  4. 举报主题；
  5. 管理员领取/处理为隐藏；
  6. 数据库 `review_queue.status=decided`、`topics.status=hidden`。
- 申诉流程实测：受限用户提交申诉 → 管理员通过 → 用户恢复 `active`，申诉状态为 `approved`。

## 8. PostgreSQL 验证补充

- 审核链路在 PostgreSQL 上完成实测。
- 测试过程中修复了等级表 `levels.level` 的 0 值主键被自增的问题；该问题会导致 Lv0 重复插入和等级错位。
- 修复后 SQLite 与 PostgreSQL 均校正为 0–6 级。

## 前端版主操作

- 主题页顶部操作区新增「管理」菜单，仅对拥有对应权限的用户显示：
  - `topic.pin`：置顶主题 / 取消置顶
  - `topic.feature`：设为精华 / 取消精华
  - `topic.moderate`：锁定主题 / 解锁主题
- 操作提交到 `POST /t/{number}/moderate`，服务端再次校验权限，前端隐藏不作为安全边界。
- 操作成功返回原页面，并在 `audit_logs` 记录：
  - 动作：`topic.pin` / `topic.unpin` / `topic.feature` / `topic.unfeature` / `topic.lock` / `topic.unlock`
  - 原因：前端页面操作
  - 记录操作者、IP、request_id 与目标主题。
- 版主预设组默认包含 `topic.pin` 与 `topic.feature`；已有安装会一次性补齐这两个权限，不影响管理员后续自定义。
- 权限键新增：
  - `topic.pin`「置顶主题」
  - `topic.feature`「设置精华」
- 后台「用户组与权限」中可对任意用户组单独勾选这两个权限。
