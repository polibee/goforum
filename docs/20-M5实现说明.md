# M5 实现说明：商业化与支付

M5 在 M0–M4 之上落地商品、订单、支付渠道注册表、订单支付与回调幂等、退款、订阅与权益、复式账本、优惠券、对账和报表，并补齐前台收银台与后台商业化面板。

## 1. 交付范围

| 能力 | 实现 |
| --- | --- |
| 商品 | 积分包、VIP 套餐、邀请包；价格、积分、时长、上下架 |
| 渠道注册表 | `balance` / `manual` / `alipay` / `wechat`，驱动按需构建，新增渠道不改订单核心 |
| 订单 | 服务端计价、优惠券、30 分钟过期时间、状态机、渠道快照 |
| 支付 | 余额即时支付、人工确认、支付宝/微信沙箱跳转、支付回调幂等 |
| 退款 | 全额/剩余金额退款、积分回收、权益撤销、订阅取消、余额退回 |
| 订阅/权益 | `subscriptions` + `entitlements`，VIP 续期按到期时间顺延 |
| 账本 | 复式记账、幂等键、账户余额、用户余额非负约束 |
| 优惠券 | 固定金额/百分比、门槛、总量、单用户上限 |
| 对账/报表 | 按渠道与日期对账、差异记录、近 7 日收入/退款/订单报表 |
| 前台 | `/pricing`、`/checkout/:out_trade_no`、`/billing/orders`、`/billing/subscription` |
| 后台 | `/admin/billing`：商品、渠道、订单、退款、优惠券、订阅、对账、余额调整 |

## 2. 数据模型

| 表 | 说明 |
| --- | --- |
| `products` | 商品定义，`slug` 唯一 |
| `payment_channels` | 渠道定义：`driver`、名称、模式、启用、配置 JSON |
| `orders` | 订单与商品快照；`out_trade_no` 唯一；金额单位为分 |
| `payment_transactions` | 支付流水；`(channel_code, channel_trade_no, type)` 唯一 |
| `payment_notify_logs` | 回调日志；`(channel_code, event_id)` 唯一 |
| `refunds` | 退款单，记录操作人、原因、渠道退款号 |
| `coupons` | 优惠券模板与使用计数 |
| `coupon_redemptions` | 优惠券核销；`(coupon_id, order_id)` 唯一 |
| `billing_subscriptions` | 订阅记录，续期顺延 `ends_at`（M7 从共享 `subscriptions` 拆分） |
| `entitlements` | 权益；`(user_id, resource_type, resource_id)` 唯一 |
| `ledger_accounts` | 账本账户；`(owner_type, owner_id, currency, kind)` 唯一 |
| `ledger_transactions` | 账本交易；`idempotency_key` 唯一 |
| `ledger_entries` | 借贷分录与余额快照 |
| `reconciliation_runs` | 对账批次 |
| `reconciliation_diffs` | 对账差异 |

金额统一以最小货币单位（分）存储，避免浮点误差；币种默认 `CNY`。

## 3. 订单状态机

```
created ──余额支付/零元单──> paid
created ──创建渠道参数────> pending ──支付成功──> paid
pending ──渠道失败────────> failed
paid    ──退款────────────> refunded
```

- 状态迁移使用 `WHERE id = ? AND status IN (...)` 的 CAS，避免并发重复支付。
- 支付回调先写 `payment_transactions`，唯一键冲突即视为重复通知；账本交易以 `order:{id}:paid` 幂等。
- 重复支付返回成功但不再发放权益或积分，保证客户端重试安全。

## 4. 账本口径

- 站内余额支付：用户 `balance` 借记，系统 `revenue` 贷记。
- 第三方支付：系统 `clearing` 借记，系统 `revenue` 贷记；退款时 `refund` 借记，用户 `balance` 贷记。
- 余额调整：系统 `adjust` 与用户 `balance` 对开。
- 仅用户 `balance` 账户禁止负余额；系统清算/收入账户允许负数，用于表达待结算与累计收入。
- 每笔交易分录借贷必须相等；账户余额与分录 `balance_after` 同事务写入。

## 5. 权益与订阅

- `vip_plan` 支付成功后创建或顺延订阅，并 upsert `entitlements(resource_type=vip, resource_id=product_id)`。
- 退款时撤销该订单来源的权益，并取消该订单创建的订阅。
- 积分包支付成功后通过 `gamification.Points.CreditExternal` 入账；退款前先 `SpendExternal` 扣回积分，积分不足则拒绝退款，避免“退了钱还留下积分”。

## 6. 渠道

| 驱动 | 行为 |
| --- | --- |
| `balance` | 校验余额后即时扣款并完成订单 |
| `manual` | 生成待支付订单，后台“确认收款”完成支付 |
| `alipay` / `wechat` | 开发环境跳转 `/payments/mock/:out_trade_no` 模拟成功；生产环境禁用模拟入口 |

渠道由 `payment_channels` 表驱动，启用/停用即时生效。新增真实渠道时实现 `Gateway`（`Create`/`Refund`/`VerifyNotify`/`Ack`）并在 `buildGateway` 注册即可，订单、账本、后台无需改动。

## 7. 路由

| GET | `/pricing` | 商品列表、余额、渠道选择 |

后台操作均写入审计日志（退款、余额调整等）。

## 8. 对账与报表

- 对账按 `channel_code + biz_date` 拉取当日已支付/已退款订单与成功支付流水，逐单比较金额。
- 差异类型：`missing_or_mismatch`（本地有单、渠道金额缺失或不一致）、`channel_only`（渠道有流水、本地无对应订单）。
- 对账批次先落库再写差异，差异通过 `run_id` 关联。
- 报表输出近 7 日每日收入、退款、订单数；收入口径包含已退款订单，退款单独列示，便于核对净收入。

## 9. 验证

已通过：

- `go build ./...`
- `go test ./...`
- `go vet ./...`
- 端到端冒烟（开发环境、全新 SQLite）：
  1. 安装向导创建管理员；
  2. 后台创建积分包、VIP 套餐与优惠券；
  3. 积分包使用支付宝沙箱 + 优惠券下单，实付 5.00，沙箱支付成功，积分 +1000；
  4. 重复访问沙箱支付不重复发放积分/流水；
  5. 后台充值余额 50.00，余额购买 VIP 30 天，订阅与权益生效；
  6. 后台退款 VIP 订单，订阅取消、权益撤销、余额回到 50.00；
  7. 人工渠道下单，后台确认收款，积分再次 +1000；
  8. 支付宝对账差异 0，后台报表与订单列表正常渲染。

## 10. 当前边界

- 支付宝/微信为沙箱驱动，未接入真实签名与证书；生产接入需补充 `VerifyNotify` 验签、金额/币种校验与回调路由。
- 退款统一退回站内余额，未调用渠道原路退款；真实渠道需在 `Gateway.Refund` 中实现并记录渠道退款号。
- 单币种（CNY），不含汇率换算与自动续费。
- 回调日志表已建，当前沙箱与人工确认路径未写入；接入真实回调时在 `VerifyNotify` 后落 `payment_notify_logs`。
